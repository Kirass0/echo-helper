# 19: Calculation scheduling, pending display, cache budget and failure

**Parent:** [Spec: Echo Helper web app](../../web-rewrite/spec.md) (§3 "Caching", §11)

**Look:** the faded results and their message follow `.stale-wrap` and `.stale-msg` in variant D of the [ticket 11 prototype](../../web-rewrite/prototypes/11-visual-direction/index.html) (`?variant=D&strat=unfinished#upgrade-strategy`).

**What to build:** On slow tables or slow devices the app stays honest and responsive. The visible tab is calculated first. A result that takes longer than about 300 ms fades and says "Calculating…" in a slot kept free for it. Memory stays bounded, and if the worker crashes the app recovers once before showing a clear message in the affected area.

**Blocked by:** 11 (Echo distribution chart), 17 (Compare two strategies)

**Status:** done

- [x] Job order: the visible tab before the hidden one (the hidden tab still calculates); in Echo Evaluation the focused table first, then the list top to bottom; in Upgrade Strategy A before B
- [x] Each edit sends a request that replaces any queued one; outdated work is dropped between jobs; a running job finishes and its outdated result is discarded; the worker is never terminated to cancel and there is no Cancel action
- [x] Nothing changes for the first ~300 ms; then each still-pending result fades and shows "Calculating…" in an always-reserved slot: each Echo Evaluation table row, the results heading and the chart, and each strategy's results; the fade is the same as the unfinished-rule fade; no progress bar
- [x] Caches are in worker memory only, evicted least-recently-used under a fixed budget of about 10M entries; the focused table's caches are never evicted; an evicted table is recalculated on demand with the pending fade
- [x] If a job throws or runs out of memory, the worker is restarted once and the job retried; if that fails too, each affected results area shows "Couldn't calculate this. Reload the page to try again." while the rest keeps working, and nothing is reported anywhere
- [x] Tests cover newest-wins dropping, job order and the restart-then-message path (e.g. with an injected failing job)

## Comments

**2026-11-22, from the second review of PR #2:** a job that throws inside the worker stalls the rest of its request today. In `src/calculation/newestInputWins.ts`, `runNext` clears `scheduled` before calling `jobs.run`, and `scheduleNext` only runs after a successful post. So when one listed table's job throws, the tables queued after it are never calculated and keep showing "—" or an old result until the next edit. `createCalculator` also sets no `onerror`, so the app is never told. When building the restart-then-message path, make sure a failing job doesn't stop the queue (e.g. `try`/`finally` around `jobs.run` so `scheduleNext` still runs) and that the failure reaches the app. Add a test with an injected failing job followed by a healthy one.

**2026-11-22, implementation notes:** the app tells the worker which tab is visible (`Calculator.showTab`, a `visibleTab` message, sent from a layout effect so it goes before the tabs' requests); the worker runs that tab's next job first, deciding again between jobs, and About keeps the last tab's order. A throwing job no longer stalls the queue: the worker catches it, posts `{ kind: 'failed', id, tableName? }` and goes on. The app (`createCalculator`, which now takes a function that starts a worker) restarts the worker on that message or on the worker's `error` event (a crash says nothing of which job it was, so every job still to come counts as failing), and sends again what of each newest request is still to come, Echo Evaluation cut down to the tables still to come. A job that fails again after its restart is given up: `onFailed` (a new optional last argument of `evaluate`, `calculateUpgradeStrategy` and `topEchoScores`) is called and the rest go on; each new input has its own retry. The `error` event is `preventDefault`ed, so nothing is reported. A worker that dies with no `error` event at all can't be noticed; its results stay "Calculating…". Pending display: `useLongPending` (`src/ui/`) turns a key on after 300 ms of pending without a break. On Echo Evaluation each row has "Calculating…" in its line under the results (where the target error line is kept free), the results heading at its right end in room it always keeps, and the chart over the plot's top right; on Upgrade Strategy the results panel at its top right and, while comparing, each strategy's heading before Edit/Done. `HeldStrategy.state` is `'done' | 'calculating' | 'failed'`; a pending example's thresholds count as pending results. Results calculating or given up stay, faded as for an unfinished rule. "Couldn't calculate this. …" is a block in the look of the prototype's `.stale-msg` above the results (in a row, one line); unlike "Calculating…" it pushes the boxes down, as it only appears after a failure. An example whose thresholds fail leaves them empty, so the rule is unfinished. Cache budget: Echo Evaluation's kept tables (whole-table distribution, finishing and shifted tables per listed table) are counted in Echo Scores and evicted least recently used past `CACHE_BUDGET` = 10M, never the focused table's or the one just calculated. Upgrade Strategy and the examples' Top x% Echo Scores keep only the latest Weight Table's tables, as before, outside that count. Against the ticket 11 prototype the static states are unchanged; `npm run compare:prototype` can't set up the pending or failed states, and the prototype has no "Calculating…" or failure design beyond `.stale-wrap` / `.stale-msg`, which the fade and the failure block follow. They were checked in screenshots with a stubbed Worker.

**2026-11-22, review of tickets 15–19:** cache budget: one `CacheBudget` (`src/calculation/cacheBudget.ts`) now counts what every job keeps, Upgrade Strategy's finishing tables and an example's Top x% distribution included, and evicts the least recently used past `CACHE_BUDGET`; the focused table's and Upgrade Strategy's current table's are never evicted, nor the one just used. Job order: Strategy A's Top x% Echo Scores and strategy run before Strategy B's. Failure: the worker is restarted once per page load, as spec §11 says. The first job that throws, or a crash, restarts it and sends again what is still to come; a job that fails after that is given up without a restart, and the worker keeps running the rest. If the restarted worker crashes too, everything still to come and every later request is given up, so each results area shows "Couldn't calculate this. Reload the page to try again." A failure reported for an outdated request restarts nothing. The worker's visible tab now uses the app's tab ids (`evaluation`, `strategy`). The failure message still pushes the results down when it appears, as noted above.
